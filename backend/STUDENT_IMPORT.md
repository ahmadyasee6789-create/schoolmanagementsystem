# Student import

Apply the schema migration before starting the updated backend:

```powershell
cd backend
.\venv\Scripts\python.exe -m alembic upgrade head
```

Use the same database configuration as the backend being deployed. The migration adds
`student_import_batches`; it does not modify existing students. Deploy frontend and
backend together because confirmation now uses a validated batch rather than another
file upload.

## Workflow

1. **Upload:** `POST /students/import/preview` accepts multipart `file` (`.xlsx`,
   UTF-8 `.csv`, or `.tsv`). It stages source data for 24 hours, detects header rows,
   suggests mappings, and lists classrooms in the active session. Hidden and
   non-student sheets start unchecked. Older `.xls` files must be saved as `.xlsx`.
2. **Map:** choose sheets, header rows (first 20 rows), student fields, and either
   a fixed classroom per sheet or mapped Grade/Section columns. Column positions,
   rather than labels, distinguish duplicate headers. Unmapped values are ignored.
3. **Validate:** `POST /students/import/validate` accepts `batch_id`, `sheets`,
   `enrollment_date`, and `date_format` (`iso`, `dmy`, `mdy`). Each sheet supplies
   `sheet_index`, `header_row`, `fields` (zero-based column index to field), and
   optional `classroom_id`. No students or enrollments are created. The response
   includes a new `validation_id` and every candidate row with source coordinates,
   normalized student details, errors and warnings. Invalid rows cannot be selected.
   Possible name matches in the file or database require manual selection; students
   are never automatically merged or overwritten.
4. **Confirm:** `POST /students/import/confirm` accepts `batch_id`, `validation_id`,
   and selected `row_ids`. One transaction creates the selected students and their
   enrollments and marks the batch complete. Database failure rolls everything back.
   Repeating confirmation returns the saved result without inserting more students.

Each route enforces the existing student write roles. Batches are scoped to the
uploading user, organization and active session. A different session, changed
classroom, new matching student, expired batch or stale validation requires a new
upload or validation. Row locks serialize confirmation of a batch and imports within
an organization on PostgreSQL. Source data is cleared after successful confirmation;
expired staging rows are reclaimed on the organization's next upload.

Phone values stay text, including explicitly zero-padded Excel numbers. Unusual
values produce warnings without inventing missing digits. Full names are split at
the first whitespace for the existing first/last-name schema, retaining the remainder;
single names use an empty last name. Fee fields are never imported. Admission and roll
numbers continue to be generated by the existing student/enrollment functions.

Limits: 10 MB per upload, 50 worksheets, 10,000 total source rows and 100 columns.
Mapped formulas require source values; unmapped formulas are ignored.

## Verification

```powershell
.\venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

Tests use disposable SQLite databases and in-memory synthetic spreadsheets. They do
not connect to the configured school database. PostgreSQL row-lock concurrency is
not exercised by SQLite tests.
